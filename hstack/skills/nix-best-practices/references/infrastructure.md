# Infrastructure

Rules for a flake that defines machines: host configurations, the modules they share, flake inputs, secrets wiring, and deployment. The modules inside it follow [modules](modules.md) as well.

| Rule | Summary |
|------|---------|
| One directory per machine, one file per service | A machine's directory imports the shared base and its own service files. Extend an existing shared module before copying its settings into a machine. A shared module sets overridable defaults with `lib.mkDefault`, so a machine changes them without `mkForce`. |
| Every input follows | Each input that takes `nixpkgs` gets `inputs.nixpkgs.follows`, and an unused transitive input is cut with `follows = ""`. Inputs only development needs go in a separate development flake or partition. |
| The lock file changes on purpose | `flake.lock` changes only for an input update the task asks for. No temporary pins or branches unless the change requires them. |
| Every machine is a check | Each machine's `config.system.build.toplevel` is a flake check, so CI builds every machine on every change. The workstation does not build them; see "Build only on request". |
| Secrets are runtime files | The repository's secret tool (sops-nix, agenix, clan vars) puts a file on the machine. A service reads it through `EnvironmentFile` or `LoadCredential`, and the secret restarts the units that use it. |
| Generated files come from their task | A report, inventory, or hash file that a task writes is regenerated by that task and its diff reviewed, not edited by hand. The next run would overwrite the edit. |
| The controller is not the target | The machine that evaluates or deploys can differ from the target in system, shell, and system features. A command or path that works on the controller is not proof for the target. |
| Review what a rollout touches | Before a deploy, say what activation restarts or kills, which state directories the backup covers, and which monitoring, DNS, or inventory entries a new service needs. |
| Check the running system after a deploy | A successful evaluation or build does not prove runtime behavior. After a deploy, check the affected units, listeners, firewall reachability, metrics, backups, and user-visible endpoints. |
| Updates are automated per kind | The lock file is updated by a scheduled job that opens a pull request, and packages by their updater, one pull request per package. A bump goes through that updater, not through hashes edited by hand. |
